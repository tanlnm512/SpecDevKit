spec-brainstorming

The five-stage flow

From a raw idea to a design specification the user owns. Three independent lenses argue where the idea could go, why it might die, and what the smallest honest version is; the user — never the panel — picks the direction; the run ends with a durable artifact and /spec named as the next step.

Stage 1 — context discovery

Exactly ONE questionRestate the ask, then one clarifying question aimed at the fuzziest of problem / audience / constraints — never a list, never a form. The kebab-case name is stated in passing, not asked.
Still fuzzy after one follow-up?Proceed on what is known, assumptions named in the artifact. An interview is not the goal — enough ground for three lenses to argue is.

Stage 2 — the perspective panel

spawned fresh, in parallel — none sees another's output
The Visionaryceiling · leverage · love · adjacency — the generous reading, grounded in the stated problem, never sci-fi.
The Cynicfatal assumptions · adoption blockers · hidden costs · kill criterion — the pre-mortem, real criticism not theater.
The Minimalistcore value · day-one cut list · fastest proof · scope guard — what survives if 90% is cut.
each returns a digest only — angle · pitch · points · watch; presented distinctly labeled, no synthesis between them

Stage 3 — the trade-off matrix

One tablepros · cons · implementation speed · best-when per angle — speed is a coarse word plus one clause why, not an estimate.
No recommendationThe table carries no verdict — the Cynic's pros are honest, "best when" states the situation. The next move is the user's.

Stage 4 — socratic refinement

Single questionsStrictly one per turn, each shaped by the previous answer — sharpen scope, surface the blend, kill options. Suggested answers allowed; the question is always singular.
Soft cap fiveThen stop asking: summarize the selection or blend — what was rejected and why — and ask for confirmation as the final question.

Stage 5 — handoff

brainstorms/<name>.mdWritten from the pinned template: Direction (selected + rejected, with reasons) · Problem Statement · User Personas · Core MVP Features + out-of-scope · Risk Mitigations with early warnings and kill criteria.
Collision → one questionAn existing file is read first: overwrite, or version the name — never a silent clobber. Nothing is ever written under specs/.
Next step: /spec <name>The doc is intent input for the spec intake — pointed at, never parsed. The commit is the user's.
